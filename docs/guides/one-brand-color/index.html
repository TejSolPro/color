From one brand color
to interface roles.

Your brand color is an input, not a complete system. Give it a specific job before generating anything around it.

A logo may need one memorable color. An interface needs colors for surfaces, text, actions, borders, focus, feedback, disabled states, and interaction. Treating the original brand color as the answer to all of these creates inconsistency—and often poor contrast.

1. Choose the first job

Decide where the brand color matters most. For many products, that is the primary action. For editorial products, it may be emphasis or navigation. Assigning one job prevents the color from becoming decoration everywhere.

2. Select the canvas and text independently

Start with a neutral canvas and a text color that can carry long-form reading. The brand color should not force every neutral to share its hue. Test the exact text-and-canvas pair at the sizes you will use.

3. Derive states, not a rainbow

Generate only what the interface needs: a hover state, a subtle background, a visible focus ring, and perhaps a selected state. Each derived color should record its parent and transformation.

4. Test pairs in context

Contrast is a relationship between foreground and background. Test button text on the primary color, body text on the canvas, links on their actual surfaces, and focus indicators against adjacent colors.

5. Name by purpose

--color-primary tells an implementer how to use a token. --red-600 only describes its appearance. Keep primitive values when helpful, but expose semantic roles to components and AI agents.

A small first system is stronger than a large speculative palette.

Begin with the roles you can explain and test. Add new roles when a real interface requirement appears—not because a generator can produce more swatches.
